# بيت الكرم — خطة تنفيذ متكاملة خلال أسبوع واحد

**الحالة:** خطة تنفيذ ومحكّ جاهزية، وليست وعداً بإطلاق عام في اليوم السابع.  
**نقطة البداية:** الملفات الحالية تخطيط وتصميم فقط؛ لا يوجد تطبيق Flutter أو خدمة NestJS أو مشروعا Next.js منفّذون في مساحة المشروع.  
**صاحب التنفيذ:** شخص واحد يستعين بوكلاء AI في مهام محددة، ويتولى بنفسه الدمج والقرارات والاختبار النهائي.  
**مدة المحاولة:** 7 أيام، كل يوم سبرنت قصير يُغلق بجزء يعمل من الواجهة إلى قاعدة البيانات.  
**شرط الإطلاق:** كل الوظائف التي سيعلن عنها المنتج تعمل ببيانات حقيقية وتنجح في اختبارات القبول؛ لا يُستبدل هذا الشرط بتاريخ ثابت.

## 1. حدود ما نعرفه وما لا نعرفه

- المخططات توثق **56 شاشة/حالة لتطبيق العميل و39 للإدارة**، و16 مساراً لهما. التصميم الفعلي يحتوي 85 لوحة منها خمس أمثلة عربية. الموقع له ست صفحات و8 مسارات زائر.
- التقنية المذكورة في التخطيط: **Flutter** للتطبيق، **Next.js** للوحة الإدارة والموقع، و**NestJS** لخدمة مشتركة. لا توجد وثيقة معمارية تحدد قاعدة البيانات أو العقود البرمجية أو بيئة النشر، لذلك تبقى هذه قرارات تنفيذية لهذه الخطة.
- قائمة الـ52 صنفاً والأسعار والعناوين وتواريخ قصة المطعم في الملفات تمثل **بيانات تصميم** إلى أن تُعتمد تشغيلياً. لا تدخل الإنتاج افتراضاً.
- معاينات الخرائط الحالية ليست خرائط Google الحية. لا يوجد مفتاح Google Maps حتى الآن؛ استخدام خرائط حقيقية يتطلب مفتاحاً وفوترة وإحداثيات فروع ونطاقات توصيل صحيحة.
- مسار الموقع W2 يذكر «طلباً من المتصفح» لكنه يصرح بأن تصميمه مستقل ولا يوجد ضمن الصفحات الست. لا يظهر خيار طلب ويب في إطلاق الأسبوع إلا بعد تصميمه وبنائه واختباره؛ زر التوصيل يذهب إلى التطبيق/رابط تنزيله حتى ذلك الحين.
- التتبع الحقيقي لموقع المندوب يحتاج مصدر إحداثيات. لوحة الإدارة المصممة لا تتضمن واجهة مندوب؛ نضيف واجهة تشغيل صغيرة للمندوب أو تكاملاً مع نظام توصيل موجود، وإلا يُعرض **تتبع حالة الطلب** فقط بصدق.

### حقيقة الجدول

تنفيذ كل ما سبق بواسطة شخص واحد، من صفر كود، مع دفع إلكتروني وخرائط حقيقية وتطبيقين منشورين واختبارات تشغيلية، **لا يمكن ضمانه خلال سبعة أيام** حتى مع وكلاء AI. الخطة التالية تعطي ترتيباً صارماً للمحاولة وتكشف العوائق مبكراً. نهايتها الممكنة هي نسخة مرشحة للإطلاق أو تجربة مغلقة؛ الإطلاق العام يحدث فقط إذا اجتازت البوابات في §7. إذا كان حساب Google Play الشخصي جديداً، قد يفرض اختباراً مغلقاً مدته 14 يوماً قبل إتاحة الإنتاج، وهو وحده يتجاوز سقف الأسبوع [1].

## 2. تعريف النطاق قبل كتابة الكود

| المسار | الوظائف التي يجب أن تعمل فعلاً | الواجهة المقابلة |
|---|---|---|
| اكتشاف المطعم | اللغة، الضيف، الفروع والمواعيد والموقع، المنيو، البحث والتوفر | تطبيق + إدارة الفروع/المنيو + الموقع |
| بناء الطلب | خيارات الأصناف، السلة، عنوان أو استلام، منطقة التوصيل، سعر نهائي محسوب في الخادم | تطبيق + إعدادات الإدارة |
| تأكيد الطلب | OTP، دفع كاش/بطاقة/محفظة حسب المعتمد، رقم طلب، تحديث الإدارة | تطبيق + لوحة الطلبات + API |
| الوفاء | قبول/رفض، تجهيز، إسناد مندوب، تتبع حالة/موقع، إشعارات، سجل الطلبات | تطبيق + إدارة + واجهة مندوب/تكامل |
| ما بعد الطلب | إلغاء/استرداد حسب السياسة، تقييم، دعم، إعادة طلب | تطبيق + صندوق الدعم + API |
| الحجز | توافر فعلي لكل فرع، حجز وتعديل/إلغاء، متابعة الإدارة | تطبيق + إدارة + نموذج الموقع |
| النمو والعلاقة | عروض، كوبونات، ولاء، مفضلة، حملات، CRM، تقارير | تطبيق + إدارة + الموقع حيث يلزم |
| إدارة المؤسسة | الموظفون والأدوار، صلاحية الفرع، سجل التغيير، الإعدادات | لوحة الإدارة + API |
| الموقع | الصفحات الست، الفروع، المحتوى، المناسبات، الأخبار، الاشتراك، الروابط | موقع Next.js + إدارة محتوى/API |
| الجودة العامة | العربية/الإنجليزية حيث يظهر مبدّل اللغة، حالات الخطأ والفراغ، الخصوصية، إمكانية الوصول | جميع الواجهات + API |

**كل صف يُقسَّم إلى قصص عمودية صغيرة.** لا تُغلق قصة بعنوان «شاشة المنيو» إلا إذا كانت بياناتها تأتي من API حقيقي، ويتغير ما يراه العميل بعد تعديل الصنف من الإدارة، وتنجح حالة النجاح وحالة الخطأ في الاختبار.

## 3. طريقة العمل التي تمنع تفاوت الواجهة والخادم

1. **عقد واحد لكل قصة:** في بداية الجزء اليومي تُكتب حقول الطلب/الاستجابة، الأخطاء، الأدوار، حالات الفراغ، وأمثلة بيانات حقيقية. يصدر NestJS وصف OpenAPI، وتُولّد منه أنواع/عملاء الواجهة. لا تعتمد الواجهات على حقول مخترعة محلياً.
2. **وكلاء AI يعملون على شرائح عمودية:** مهمة الوكيل تشمل تعديل API وقاعدة البيانات والواجهة المعنية واختبار العقد معاً، أو يعمل وكيل ثانٍ على شريحة مستقلة. تُمنع مهمات «ابنِ كل الباك إند» أو «حوّل كل الشاشات» المنفصلة.
3. **دمج يومي على بيئة staging واحدة:** لا تُعتبر واجهة ببيانات وهمية منجزة. يمكن استعمال mock خلال ساعات التطوير، لكن يجب إزالته أو عزله عن مسار القبول بنهاية اليوم.
4. **حد عمل مفتوح:** قصتان عموديتان كحد أقصى قيد التنفيذ للشخص الواحد؛ لا تُفتح الثالثة قبل دمج واختبار واحدة. الوكيل يراجع التغييرات، وصاحب المشروع يقرّ قرار الدمج.
5. **مراجعة التغييرات المتقاطعة:** أي تعديل في السعر أو حالة الطلب أو صلاحية الموظف يعاد اختباره من تطبيق العميل ولوحة الإدارة والموقع المعني. تغييرات قاعدة البيانات لها migration وخطة رجوع.
6. **برهان يومي:** شاشة تعمل على جهاز/متصفح، طلب API حقيقي، سجل قاعدة بيانات، اختبار تلقائي للمسار، ورابط نسخة staging. العدد الكبير للشاشات المنسوخة من التصميم لا يُحسب تقدماً إذا كانت السلوكيات غير موصولة.

### البنية التنفيذية المقترحة

- مستودع واحد منظم إلى `apps/customer_flutter` و`apps/admin_next` و`apps/site_next` و`services/api_nest` و`contracts/openapi` و`docs/decisions`. هذه أسماء تنظيمية مقترحة وليست كوداً موجوداً الآن.
- PostgreSQL للبيانات الأساسية. حفظ الأموال بوحدة أصغر من الجنيه (قروش) أو نوع decimal مضبوط؛ الخادم وحده يحسب الإجمالي والخصم ورسوم التوصيل، ويحفظ لقطة السعر داخل كل طلب.
- تخزين ملفات للصور، خدمة SMS للـOTP، قناة push، Google Maps بمفاتيح مقيدة لكل منصة. تُعزل الخدمات الخارجية خلف واجهات قابلة للاستبدال في الاختبارات.
- صلاحيات على مستويين: الدور **والفرع**. مدير فرع لا يرى طلبات أو عملاء فرع آخر. لكل تغيير في السعر، المنيو، الصلاحيات، والاسترداد سجل تدقيق.
- إنشاء الطلب والدفع بآلية منع التكرار عند إعادة المحاولة، ومعالجة callbacks الدفع بشكل لا ينشئ طلباً أو رداً مالياً مرتين.
- حالات الطلب تُعرف كآلة انتقالات واحدة في الخادم حسب النوع (توصيل/استلام/حجز)، وتستهلك الواجهات نفس القيم؛ لا يحتفظ التطبيق واللوحة بمنطق حالات مستقل.

## 4. بوابة الجاهزية قبل بدء اليوم الأول

| لازم يتوفر أو يُحسم | أثر غيابه في أسبوع الإطلاق |
|---|---|
| بيانات الفروع الحقيقية: عناوين، إحداثيات، ساعات، أرقام، نطاقات ورسوم | اختيار الفرع والتوصيل والخريطة لا يمكن قبولها |
| قائمة وأسعار وضرائب ومكونات/حساسية وتوفر معتمدة | المنيو والـcheckout لا يصلحان لاستخدام عميل حقيقي |
| سياسة الحجز والإلغاء والاسترداد والولاء والتوصيل | الخادم لا يملك قواعد صحيحة للتنفيذ |
| حساب Google Maps مفعل ومفتاح مقيد وفوترة | خرائط Google الفعلية غير قابلة للتشغيل [2] |
| مزود SMS، بوابة دفع وعقود الاختبار/الإنتاج، حسابات push | OTP والدفع والإشعارات لا يمكن قبولها كاملة |
| حسابا Apple/Google، نطاق الموقع، خادم الإنتاج، شهادات/أسرار | النشر العام لا يمكن إكماله |
| من يستقبل الطلبات في الفرع ومن يحدّث موقع المندوب | لا يوجد تشغيل حقيقي خلف «التتبع المباشر» |

إذا لم تتوفر هذه المدخلات، يستمر البناء ببيئة اختبار، لكن **لا تُقدَّم تلك الوظائف كجاهزة للإطلاق**.

## 6. الاختبار ملازم لكل سبرنت

| المستوى | مثال إلزامي | وقت التشغيل |
|---|---|---|
| وحدة وقواعد | التسعير، كوبون منتهي، حدود منطقة توصيل، انتقال حالة غير مسموح، حساب نقاط | مع كل تغيير وفي CI |

## 7. تعريف «جاهز للإطلاق» — قرار GO/NO-GO

لا يكفي الوصول لليوم السابع. يجب تحقق جميع النقاط التالية:

1. **تتبّع تغطية كامل:** لكل واحدة من 95 شاشة/حالة في الـSitemap والصفحات الست: منفّذة أو موثَّق أنها نمط مشترك يعمل؛ لا عنصر معروض يقود إلى طريق مسدود. ثمانية مسارات الموقع و16 مسار التطبيق/الإدارة ناجحة على staging.
2. **تشغيل الطلب والمال:** كل أنواع الطلب المعروضة للناس (توصيل/استلام، والحجز حيث يُعلن عنه) تنتهي وتُدار من الفرع. مجموع السعر والخصم والضريبة والرسوم صحيح، فشل الدفع والاسترداد والإلغاء مجرّب، ولا تكرار عند إعادة المحاولة.
3. **بيانات وخدمات حقيقية:** الفروع ومواعيدها وحدود التوصيل وأسعارها معتمدة؛ مفاتيح Google ومزود الدفع والـSMS وpush جاهزة ومقيدة؛ فريق الفرع قادر على استقبال الطلبات. لا خريطة أو موقع مندوب تمثيلي على أنه حي.
4. **أمن وخصوصية:** منع كشف بيانات عميل/فرع آخر، صلاحيات الإدارة و2FA، تحديد محاولات OTP، حماية الأسرار، حذف الحساب/البيانات بحسب سياسة المنتج، وسجلات تدقيق للعمليات الحساسة.
5. **جودة قابلة للقياس:** لا عطل يمنع الطلب أو الدفع أو الحجز؛ مسارات E2E الأساسية خضراء على Android وiOS والمتصفحات المستهدفة؛ العربية والإنجليزية لا تكسران الواجهات؛ الأداء والنسخ الاحتياطي والاستعادة تحت تجربة فعلية.
6. **إطلاق يمكن الرجوع عنه:** مراقبة أخطاء وتنبيهات، مسؤول استجابة، إصدار قاعدة بيانات قابل للاستعادة، نشر تدريجي لفرع واحد ثم التوسع بعد مراقبة الطلبات الحقيقية.
7. **جاهزية التوزيع:** صفحات المتاجر، بيانات الخصوصية، حسابات المطور، الاختبار المغلق والمراجعات المطلوبة. شرط Google Play المذكور في §1 قد يمنع الإطلاق العام خلال أسبوع حتى لو انتهى الكود [1].

**إذا فشل أي شرط:** النتيجة «نسخة اختبار/بيتا» مع قائمة نواقص محددة، وليس إطلاقاً عامًا باسم بيت الكرم. تاريخ الإطلاق التالي يُحدَّد بعد سد النقص؛ لا تضاف وظيفة شكلية لإغلاق خانة.

## 8. ما يُقاس منذ أول مستخدم

- نسبة من شاهد المنيو ثم بدأ checkout ثم أكمل الطلب، ومعدل فشل الدفع حسب السبب.
- زمن قبول الطلب وزمن التجهيز والتوصيل لكل فرع، ونسبة الإلغاءات والاستردادات.
- أخطاء التطبيق وAPI، تأخر الأحداث والإشعارات، وفشل الخرائط/OTP.
- حجوزات مكتملة ومرفوضة، واستخدام الكوبونات، وعودة العملاء للطلب.
- مصدر زيارات الموقع والتحويل إلى تنزيل التطبيق أو حجز/استفسار.

تُجمع هذه الأحداث دون كشف بيانات شخصية في سجلات التحليل. تُراجع بعد أول استخدام فعلي لتصحيح الأولويات.
